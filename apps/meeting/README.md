# 会议记录与会议纪要工作台

负责人：summerchaserwwz。原会议入口见 #29、#36；会议纪要工作台见 #227。工作台与原入口共享 `meeting` 记录和平台版本库，不复制会议业务库。

## 需求七问

### 1. 触发

会后保存文字或录音、查找历史纪要、核对原话、定稿和跟进分派事项。工作台提供工作概览、会议档案和待办跟进；原会议应用位置保留。

### 2. 使用者与确认人

查看沿用应用与项目授权。具有 operate 且被指定为整理负责人的经办人可保存、定稿和派发；显式 admin 可管理。指定任务负责人即使只有 view，也可填写本人事项进展。普通定稿不经过领导审签，需要正式审签时转公文协作。

### 3. 输入

新建需要标题、会议日期，整理负责人默认为当前用户。可粘贴文字、留空后补材料，或使用原上传接口保存录音。真实上传在未配置服务时明确失败并保留录音，不使用固定示例文字。仅显式示例或内容与公开合成样本完全相同的录音使用演示转写。

### 4. 处理步骤

1. 文字逐段保存出处；音频走实例注入的真实转写适配器与持久任务。
2. 从档案直接打开纪要，内容分类与原文并排核对；模型或原文摘录候选先比较、再采用，不自动覆盖。
3. 保存必须携带当前 baseVersion，来源纠错形成新来源版本并标记纪要待复核。
4. 经办人确认内容、依据和行动项后定稿。定稿保存平台记录版本，后续修订保留旧版。
5. 派发验证在用成员、会议查看权限、来源段落及明确年月日；重复派发只保留同一派发标识。
6. 负责人办理、完成；整理负责人可说明原因取消或重开。工作台与收件箱读取同一状态。

### 5. 确认依据

资料处理、纪要定稿、事项进展独立显示。引用使用段落 ID 和来源版本；旧音频相同时间戳仍区分段落。定稿不表示事项办结或正式签发。未定负责人或模糊期限可保存为候选但不能派发。到期时间按北京时间选定日期 23:59。

### 6. 输出

会议档案、固定定稿快照、可追溯的派发与进展、真实 DOCX。企业关联选择有权查看的已有诉求并保存 ID/来源，状态以企业服务为准；新诉求先到企业工作台登记。转公文使用 #228 的受权固定版本来源契约。离线 Word 复用 #228 的 `JKWord` 工具，HTTP 导出由实例桥接使用现有 python-docx。

### 7. 验收样本

`tests/test_workbench.py` 验证真实 HTTP 的版本冲突、来源纠错、重复时间戳、定稿、授权、幂等、收件箱同源完成、跨模块回链和真实 Word 回读，以及任意音频失败和真实转写适配。`web/tests/contract/meeting-workbench-browser.cjs` 从页面录入文字到定稿、派发、刷新和查看历史，包含 1440/1280/390 布局与权限行为。示例均标为虚构，不向成员派发。

## 接口与存储

新增接口统一在 `/api/apps/meeting/workbench`，详见 [实施说明](../../docs/plan/会议纪要工作台实施说明.md)。原 `/meetings` 的读取保持兼容；工作台记录的旧式无版本写入提示转工作台。实例关闭通用 meeting records 写入口，防止绕过负责人和状态校验。

定稿纪要保存在 `data.minutesEdit`，状态 `minutesStatus`，`finalizedVersion` 绑定平台记录版本。任务唯一派发记录仍在会议 `data.todos[].assignment`；原 `jkq_meeting_todo_done` 表扩展状态、说明与历史，旧行自动保留为已完成，不增加第三份完成状态。

`jkq/meeting_bridge.py` 在实例启动时注入转写、办理状态、目标资源授权及 DOCX 服务。会议 API 不读取环境变量，不直接使用平台数据库或增加依赖白名单。模型或真实转写服务不可用时人工录入、编辑、定稿及导出仍可继续。

已派发事项保留内容与来源版本。经办人可说明原因改派改期；接收人、状态行、通知与审计在同一个 SQLite 事务中更新，完成或取消事项必须先明确原因重开。可将历史定稿恢复为新的待核对草稿，旧定稿及当前任务进展保留；会后补充自动记补充人、时间和核实出处。空记录可后补录音原件。现场录音入口沿用原应用，本轮未完成真实麦克风中断恢复验收。

共享规范合成样本的非负责人仅可读取示例预览：同时核对样本身份和已存音频字节与公开 demo.webm 一致，才投影对应的公开逐字稿；页面明确只读，不启动转写、不修改原记录或派发。原负责人仍走正式任务，所有写入口继续核对原负责人。离线“用示例录音”及登记的样例附件明确标为 demo；真实文件即使同名或带示例 ID 也不走此路径。
