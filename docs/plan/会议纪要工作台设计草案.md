## 定位与边界

会议纪要工作台面向政府侧经办人员和会议任务负责人，集中完成会议资料整理、纪要核对、定稿和会后事项跟进。用户既能处理新录音，也能直接找历史纪要、核对一处原话或更新自己的待办，无须每次从四步向导开始。

沿用已认可的平台方向：新增“工作台”板块，下设“企业服务”和“会议纪要”；现有四个应用的分级、位置与入口保留。工作台与应用共用业务记录和服务，对话助手以“会议助理”岗位参与当前工作。

用户已确认：普通纪要由经办人核对后确认定稿；需要正式审签时转公文协作，不给所有会议额外增加领导审核环节。“定稿”仅表示纪要内容已核对，不表示任务已完成或文件已正式签发。

首期围绕会后整理与跟进。会议预约、会议室管理、参会通知、签到、在线会议、外部企业参会门户不在本期范围。

## 一 工作台入口与首页

导航关系：工作台 → 会议纪要。它使用主内容区域，对话助手按需展开，不占用默认的档案和编辑空间。原“会议记录”应用仍可处理录音，其结果在工作台可见；从任一入口打开同一会议，使用同一个会议 ID 和记录版本。

工作台首页默认是“与我有关”：我负责整理的会议、分配给我的待办。切换“全部可见”只能扩大到账号已有权限范围，不能扩大授权。

| 首页区域 | 内容 | 点击后的行为 |
| --- | --- | --- |
| 顶部操作 | 新建会议记录；按标题、日期查找会议 | 建立记录或进入筛选后的档案 |
| 待我核对 | 我负责且已有草稿、尚未定稿的会议 | 打开该会议纪要核对页 |
| 待我派发 | 我负责且已定稿、仍有未派发待办的会议 | 打开待办核对与派发页 |
| 待我办理 | 分配给我的未完成事项 | 打开事项详情 |
| 已逾期 | 上述未完成事项中超过确定期限的部分 | 按到期时间排列；逾期是标记，不另建状态 |
| 最近处理 | 最近编辑、核对或查看的可见会议 | 直接恢复到会议详情 |
| 处理中的资料 | 转写和整理进度、失败原因、继续处理入口 | 显示真实任务状态；可离开后回来 |

导航内提供“工作概览”“会议档案”“待办跟进”三个主要页面。首页数字必须可点击并与列表筛选口径一致；不在首页放无下一步动作的大屏统计。

无会议时呈现“上传录音”“粘贴文字记录”“查看示例”三个明确入口。示例始终标记为虚构演示，进入独立演示视图，不向真实成员派发待办。

## 二 会议档案

会议档案支持按标题、日期范围、会议类型、整理负责人和纪要状态筛选。列表列出会议名称、时间、整理负责人、资料类型、纪要状态、待办完成数与逾期数。首期不承诺跨全部录音的语义检索。

新建只要求会议名称、会议日期和整理负责人，负责人默认当前用户；地点、主持人、参会人、相关企业可逐步补齐。资料可以是录音、粘贴的文字记录或暂缺资料的空记录。

选择录音后上传并整理；已有文字可以直接进入整理，原始文字同样作为出处保存。空记录允许保存会议信息，后续补材料。现场录音入口沿用既有能力，但需单独验证浏览器权限、录音保存和中断恢复，不能以演示动画替代录音。

历史会议从列表直接进入详情，不自动启动转写或重新生成纪要。旧记录没有明确定稿证据时，迁入工作台后保持草稿或待核对，不能按旧的 `done` 转写状态自动认定为已定稿。

## 三 单场会议详情

顶部固定展示会议标题、日期、整理负责人、资料处理状态、纪要状态和待办进展。三个状态分别呈现，避免一个“完成”覆盖所有含义。

详情提供“纪要”“原始资料”“待办”“关联记录”四个页签。进入已整理会议时默认打开纪要；仍在转写时显示处理进度和已有资料。

### 纪要核对

桌面上采用主编辑区与原文参考区并排布局；窄屏切为页签，保持当前段落和回听位置。会议助理按需展开，避免同时固定三个狭窄列。

纪要按“讨论要点”“已明确的决定”“待确认问题”“后续行动”组织。没有形成决定就明确表示尚未形成，不能把建议、假设或争论写成会议决定。

每段 AI 整理内容附来源引用。点击引用定位逐字稿原句；录音来源可从对应时间开始回听，文字来源定位到对应段落。引用绑定来源记录和版本，不能只依靠可能重复的时间戳。

经办人可以修改文字、校正发言人、调整分段，以及补充会后核实信息。会后补充须标明补充人、时间和来源，不能伪装成录音原话。AI 建议先以差异预览呈现，用户选择接受、修改或保留原文。

原始录音和原始转写保留；纠错形成新版本。修改被引用的来源后，对应纪要标记待复核。重新整理产生候选草稿，不覆盖已有人工作修改或已定稿的版本。

### 核对与定稿

经办人确认三类内容：讨论与决定是否区分准确、引用是否支撑结论、行动项是否正确。系统集中展示待核对引用和未确定字段。

纪要允许保留明确标注的“待确认问题”；这些问题不是伪造答案的理由，也不必阻止整份纪要定稿。尚未补齐负责人或期限的行动项可以保留为候选，不能派发。

点击“确认定稿”时绑定当前纪要版本，记录确认人和时间。定稿版本保持可读；后续修改新建修订草稿，重新确认后形成新定稿版本。旧定稿和已派发任务不被静默覆盖。

提供“导出纪要”和“转公文协作”。草稿导出有草稿标识；定稿导出标注版本和定稿时间。正式审签由公文协作承接，保留源会议及定稿版本的关联。首期采用真实 DOCX 输出，不能仅把 HTML 改成 `.doc` 扩展名就宣称完成 Word 导出。

## 四 待办跟进

会议形成的行动项先进入“待派发”。首期从已定稿纪要中选择候选事项，由经办人核实后派发；派发需要事项、唯一可识别的负责人和明确期限，并绑定来源段落与定稿版本。

“周五前”等相对日期可以给出基于会议日期的建议，但须由人确认具体日期。首期默认按北京时间的选定日期 23:59 计算到期；不能确认的期限保留为未确定，不计算逾期，也不能派发。负责人从有权参与该事项的在用成员中选择，不让模型凭姓名猜账号。

| 事项状态 | 谁能推进 | 主要操作 |
| --- | --- | --- |
| 待派发 | 有会议操作权限的经办人 | 核对内容、负责人和期限，派发或放弃候选 |
| 待处理 | 指定负责人 | 开始办理，填写进展；也可直接提交完成结果 |
| 办理中 | 指定负责人 | 更新进展、提交完成说明 |
| 已完成 | 指定负责人完成后保留记录 | 查看处理结果；有权人员可写明原因重新打开 |
| 已取消 | 有权的整理负责人 | 写明取消原因，保留历史 |

待办列表与看板是同一份记录的两种视图。默认展示“我的待办”，会议整理负责人可在权限范围内查看该会议所有待办。每张卡片显示事项、来源会议、负责人、期限和最近进展；点开可回看原话与纪要。

重复点击派发、重试请求、从不同入口操作，不得生成重复任务。改派和改期需要权限检查，记录前后值并通知涉及的在用成员。已派发内容因纪要修订发生变化时提示经办人核对；不自动改写负责人已经收到的任务。

任务完成结果在工作台、单场会议详情与个人收件箱保持一致。“已派发”不能显示为“已完成”。

## 五 与企业服务和公文协作的关系

会议中的企业问题支持两种动作：关联已有企业诉求，或确认后创建新诉求。用户先选择有权访问的企业、核对问题描述，再执行；系统保存会议、原文段落和目标诉求之间的关系，并防止重复提交。

企业诉求的办理状态以企业服务记录为准，会议工作台显示其进展和跳转入口，不另存一份独立状态。某个会议待办如果只是“登记诉求”，登记完成即可完成该待办，不能因此把企业诉求标记为办结；如目标是“解决诉求”，则显示关联诉求进展，由负责人据实际结果确认任务完成。

转公文时创建有来源关联的草稿，不能把会议定稿当作公文审批通过；也不因公文退回而删除会议定稿。

跨模块链接不扩大权限。无企业或公文权限的会议用户只能看到自己有权读取的来源信息与明确的不可访问提示；接口也必须执行同样的资源授权。

## 六 会议助理的岗位行为

工作台显示“会议助理”，作用范围明确标出当前会议或选定事项。切换到另一场会议时更新范围，不把旧会议的录音、企业或负责人带入新请求。全局对话可通过用户授权打开指定会议。

典型请求包括“总结这场会”“这条决定的原话是什么”“找出还没明确负责人的行动项”“根据刚才核对的内容修订纪要”。助手调用已有或补齐后的工具，提供带出处的结果。

读取、分析和生成候选内容可直接进行；确认定稿、派发、改派、取消任务、创建企业诉求、转公文等写入动作，展示具体内容与影响并由有权用户确认。岗位名称不改变账号权限。

来源不足时标记缺失，原音听不清时提示回听；不可把固定演示文字当作用户上传录音的识别结果。模型不可用时保留资料、人工编辑和跟进入口。

## 七 状态与记录关系

会议资料处理、纪要和待办分别建模：

- 资料处理：待整理 → 整理中 → 已整理；失败或取消是明确结果，可从保留的资料恢复。
- 纪要：草稿 → 待核对 → 已定稿；修改定稿后产生新的待核对修订，不抹去旧版本。
- 待办：待派发 → 待处理 → 办理中 → 已完成；有权用户可以取消或说明原因重开。

整理负责人完成纪要后，待办可以继续办理；所有待办完成也不能替代纪要核对。会议归档是可选的组织动作，不自动结束未完成任务。

| 对象 | 关键关联与依据 |
| --- | --- |
| 会议记录 | 标题、日期、负责人、参会人、类型；沿用既有会议 ID |
| 原始资料与纠错版本 | 录音或文字、保存时间、处理任务、逐字稿版本 |
| 纪要版本 | 会议 ID、来源版本、分段引用、编辑者、定稿人和时间 |
| 行动项与派发记录 | 稳定事项 ID、来源段落/定稿版本、收件人 ID、期限、状态及变更记录 |
| 业务关联 | 源会议/段落与企业诉求或公文记录的稳定双向关联 |

这是一份逻辑模型，不在设计阶段确定新增数据库表或迁移脚本。实施应优先扩展既有版本记录与派发标识；现有收件箱的个人完成标记需要纳入统一任务状态读写，不能再增加第三份完成状态。

## 八 权限与异常处理

沿用平台账号和应用权限，再落实到会议与事项范围。首期定稿由具有操作权限且被指定为整理负责人的经办人执行；任务负责人只更新分配给自己的事项。管理员的管理权限需显式检查，普通用户不能因知道 ID 就越权操作。

任务负责人至少必须能查看必要的来源。首期不向无权查看会议的账号派发带完整会议链接的任务；更细的按段落分享是后续范围。外部协作者默认不开放会议工作台。

上传或转写失败保留已成功保存的录音；失败位置与重试范围可见。任务处理中离开页面或切换对话不取消任务。保存冲突提示重新加载与比较版本，不直接覆盖他人修改。新增工作台的筛选与会话状态分开保存，旧应用深链保持可用。

| 会议资料 | 会议新增/列表/详情、文件保存、长任务与逐字稿编辑 | 文字记录入口、稳定来源引用、状态口径与工作概览 |

原有演示数据不能充当生产完成证据。旧会议的已派发 ID、原始资料和手工纪要应保留；历史个人完成标记映射到新任务状态时必须先做覆盖和冲突检查，不能覆盖已知完成事实。

## 十 可体验的验收样本

使用明确标识的虚构会议内容，不导入内部真实录音。准备一场多议题、多人发言的企业服务协调会，其中至少包含：

1. 已明确的决定及对应原话。
2. 尚在讨论的建议，验证不会误写成正式决定。
3. 负责人和期限齐全的行动项。
4. 缺负责人或仅有模糊期限的行动项，验证不能派发。
5. 可关联企业服务的诉求，以及一项需要起草公文的后续工作。
6. 发言人或机构名识别错误，验证回听、纠错、纪要待复核。

另设已定稿且仍有办理中任务、任务逾期、已完成、资料整理失败等档案样本，用于判断首页和看板。演示视图与真实任务分离。

产品验收以实际入口执行：

- 新用户能从空页面完成一次资料整理，不依赖隐藏演示命令。
- 能从档案直接找到纪要、从某段纪要回到原文、从待办回到所属会议。
- 手工修订在重算、刷新和切换聊天后保留，定稿旧版本仍可查看。
- 缺失负责人或期限不能派发，重复派发不重复生成任务。
- 收件箱完成任务后，工作台和会议详情显示同一结果。
- 关联企业诉求后，双方展示同一目标记录与状态，不相互误标完成。
- 账号无权访问的会议和跨模块资源不会经搜索、概览、工具或直接链接泄露。
- 真实录音必须用其自身内容产生逐字稿；没有适配器时明确不可用或进入显式演示流程，不用预置文本冒充。
- 1440px、1280px 与窄屏下，纪要、原文和助手可独立阅读操作。

## 十一 实施拆分建议

这是后续 Issue 的候选边界，本轮不创建 Issue、不创建分支、不启动实现：

1. 共享工作台导航与独立状态容器，由企业服务和会议纪要复用，避免两边各造一套外壳。
2. 会议档案、工作概览与详情布局，复用现有记录；有数据可看不等于真实整理完成。
3. 会议资料处理接入真实转写、文字来源与有依据的纪要候选生成。
4. 纪要核对、定稿版本、修订与 DOCX 输出。
5. 待办派发及状态闭环，统一收件箱、会议详情和看板。
6. 企业诉求/公文关联与会议助理上下文，完成全链路验收。

每个正式修改按用户约定先建 Issue，明确依赖和验收，再从指定基线拉分支；遵守原仓库的测试、截图和 PR 规范。保留旧应用入口作为过渡，新增入口可按功能开关逐步开放。关闭新入口只改变访问方式，不删除用户已经形成的记录。
